## v1.5.0 — 2026-08-08

`settings.json` no longer lives inside the installed package. It moves to your own per-user config directory, which makes a global install work on machines where the npm prefix is root-owned — the case that previously left the CLI unable to save anything. Existing settings are picked up automatically, and no command, prompt, or output format has changed.

### ✨ Features

- **Settings are stored per user, outside the package.** A global install can land in a root-owned prefix (`/usr/local/lib/node_modules`, `C:\Program Files\nodejs`), where writing next to the program fails. The file now follows each platform's convention:

  | Platform    | Path                                                                                        |
  | ----------- | ------------------------------------------------------------------------------------------- |
  | macOS       | `~/Library/Application Support/pvzf-console/settings.json`                                    |
  | Linux / BSD | `$XDG_CONFIG_HOME/pvzf-console/settings.json`, else `~/.config/pvzf-console/settings.json`     |
  | Windows     | `%APPDATA%\pvzf-console\settings.json`                                                        |

  `$XDG_CONFIG_HOME` is honored on macOS too, but only when set to an absolute path — the spec requires relative values to be ignored.
- **`PVZF_CONSOLE_SETTINGS` pins the file anywhere you want.** Point it at a full path for portable installs, CI runs, or to keep several profiles side by side. It takes precedence over the per-user directory.
- **The active path is visible in the app.** `[3] Settings` now prints it under *Settings file*, so there is no guessing which file a given install is reading.
- **An unwritable config directory no longer takes the session down.** Saving reports the reason instead of throwing: the CLI warns `Settings could not be saved — <path>: <reason>` and keeps the change applied for the current session.

### ⚠️ Compatibility

- **Upgrading is seamless.** A `settings.json` left inside the package by ≤ 1.4.1 is still read on first launch, then written to the per-user location on the next save.
- **The old file is never deleted.** An older install sitting alongside keeps working — but from that point the two copies no longer track each other.
- **No CLI change.** Same commands, same TUI, same Markdown reports, diff JSON, and Trello CSV output.
- **Contributors:** `saveSettings()` now returns `string | null` (a failure reason) instead of `void`, and `AppDeps.saveSettings` follows. Internal API only — nothing exported to end users changed.

### 🔧 Internal / Tooling

- New `userConfigDir()`, `legacySettingsPath()` and `SETTINGS_ENV_VAR` in `src/settings.ts`; `settingsPath()` resolves env override → per-user directory → legacy path, and returns the legacy path when no home directory can be resolved (bare containers).
- `App.persistSettings()` centralizes the save-and-warn path used by every settings mutation.
- **CI matrix extended to macOS and Windows** (`ubuntu` on Node 20 and 22, plus `macos-latest` and `windows-latest` on Node 22) — path handling and the per-user config directory behave differently per platform, so each is now exercised on every push.
- Test suite: **184 tests across 15 files**, 92.3% statement / 93.3% line coverage (75% gate). Typecheck, security lint, and the production build all pass.
- Both READMEs document the new locations, the env override, and the upgrade path; a troubleshooting row covers `Settings could not be saved`.

### 🔒 Dependencies & security

- **Security updates:** `postcss` 8.5.15 → 8.5.26 (pulling `nanoid` 3.3.18) and `brace-expansion` 5.0.5 → 5.0.9.
- **Actions:** `actions/setup-node` 6 → 7, `github/codeql-action` 4 → 4.37.4 (now pinned to an exact patch).
- **Dev toolchain:** `eslint` 10.8.0, `typescript-eslint` 8.66.0, `@types/node` 26.1.2, `@vitest/coverage-v8` 4.1.10, `globals` 17.9.0, `tsx` 4.23.7.
- **Dependabot reconfigured for supply-chain risk rather than freshness.** Version updates drop to **monthly** and now sit behind a **cooldown** (7 days for patches, 14 for minors, 30 for majors) so a hijacked release has time to be pulled before it is ever proposed. Security updates are unaffected — they ignore the schedule and the cooldown, and still open the day an advisory lands. Groups were reworked so lockstep packages (`vitest` + `@vitest/*`) can never be split across two pull requests again.
- Known and accepted: one **low** advisory on `esbuild` (GHSA-g7r4-m6w7-qqqr, arbitrary file read via its dev server on Windows). Transitive through `tsup`/`vite`, dev-only, and this project never runs `esbuild --serve`. The published package is unaffected — it ships zero runtime dependencies.
